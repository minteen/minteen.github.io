单智能体的局限性

虽然单个智能体能处理基础对话，但有明显缺陷:

  1. 无法处理所有类型问题 - 技术、订单、投诉需要不同专业知识
  2. 复杂问题需要协作 - 单个智能体知识有限
  3. 缺少路由机制 - 不知道该由谁来处理什么问题

这就是为什么我们需要多智能体系统。

智能路由与结构化输出

什么是结构化输出?

结构化输出就是让 LLM 不再返回自由文本,而是按照我们定义的 JSON Schema 返回数据。这样我们的程序就能直接解析和使用这些数据，而不用去做麻烦的文本解析。

在 AgentScope 中，结构化输出存储在 response.metadata 里,而 response.get_text_content() 仍然返回文本内容。

结构化输出的优势

  1. 格式可控 - 方便程序处理和下游逻辑分支
  2. 包含置信度 - 可以用于降级策略(置信度低时转人工)
  3. Pydantic 验证 - 自动约束数据类型和范围

多智能体协作模式

当系统涉及多个专业智能体时,需要一种机制让它们高效协作。AgentScope 提供了两种常用模式:

MsgHub 消息广播模式

MsgHub 就像一个微信群,所有参与者都在同一个群里。每个人说话,其他人都能听到。这适合需要集体讨论的场景。

特点:

  • MsgHub 内的智能体调用会自动广播消息
  • 每个智能体都能”听”到其他智能体的回复
  • 形成自然的多方对话

Handoff 任务委派模式

Handoff 模式像一个项目经理(Orchestrator)，接到任务后把它拆分成子任务，然后分派给不同的工人(Worker)去做。工人做完后把结果返回给项目经理,项目经理再汇总。

与 MsgHub 不同的是,Worker 之间互相不知道对方的存在,它们只和 Orchestrator 通信。

核心优势:

  1. 动态性: Worker 可以按需创建或预定义
  2. 上下文隔离: Worker 之间不共享上下文,减少上下文压力

两种模式对比

特性 MsgHub (消息广播) Handoff (任务委派)
协作模式 平等讨论、多方对话 层级分工、任务分派
上下文共享 所有参与者共享完整对话上下文 Worker 只收到 Orchestrator 分配的任务描述
执行流程 需要显式编排调用顺序 Orchestrator 自主决定调用哪个 Worker
适用场景 多方头脑风暴、交叉参考意见、辩论讨论 清晰任务分解、独立子任务处理、可并行化场景
通信开销 高(每条消息广播给所有参与者) 低(只在 Orchestrator 和 Worker 之间通信)
灵活性 参与者必须预先已知 可以动态创建新的 Worker 类型

选择指南:

  • 如果问题需要多个专家讨论并参考彼此的意见 → 用 MsgHub
  • 如果问题可以分解为独立的子任务 → 用 Handoff
  • 在复杂系统中,两者可以结合使用: Orchestrator 通过 Handoff 委派子任务，而某些子任务内部使用 MsgHub 进行多智能体协作讨论

Human-in-the-Loop

什么是 Hook?

我的理解: Hook 就是在智能体执行的关键节点插入自定义逻辑。就像给智能体装了”监听器”,在它回复之前或之后,我们可以插一脚进来做些事情。

在关键业务场景中,AI 生成的回复可能需要人工审核后再发给客户。AgentScope 的 Hook 机制提供了一种优雅的方式来实现人机回环,而不需要修改智能体的核心代码。

对于 ReActAgent,还有更细粒度的 Hook:

Hook 函数签名

Hook 函数的签名是固定的:

  • Pre-hook: (self, kwargs) -> dict | None
  • Post-hook: (self, kwargs, output) -> Any | None

其中:

  • self 是智能体实例
  • kwargs 是函数字典
  • output 是函数返回值
  • 返回 None 表示不做修改

总结

  1. 结构化输出 - 使用 Pydantic 模型让 LLM 返回可控格式的数据
  2. MsgHub - 消息广播模式，让多个智能体在同一个上下文中讨论
  3. Handoff - 任务委派模式，Orchestrator 分解任务并委派给 Worker
  4. Hooks - 在智能体执行前后插入自定义逻辑，实现human-in-the-loop
